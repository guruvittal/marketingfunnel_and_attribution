1. Overview & Business Context

Measuring marketing return on ad spend (ROAS) and multi-touch customer attribution across modern e-commerce channels is notoriously difficult. Digital marketing leaders operate across a complex web of Paid Search, Paid Social, Video awareness, and Email nurturing campaigns.

Traditional Relational vs. BigQuery Graph

In traditional relational databases (like standard SQL data warehouses), modeling customer attribution requires joining disparate tables with varying cardinalities (Campaigns ➔ Events ➔ Orders ➔ Line Items ➔ Products). This leads to two critical problems:

  1. The Cartesian Join Explosion (Double Counting): Joining upstream marketing budgets (1 row per campaign) to downstream order line items (millions of rows) multiplies the budget by the number of downstream rows. An email budget of $60,000 balloons into a fictitious $66.7 Billion!
  2. Complex, Fragile SQL: Multi-hop path analysis requires deeply nested CTEs, recursive queries, or heavy dimensional preprocessing pipelines that duplicate storage and introduce synchronization latency.

Google Cloud BigQuery introduces two revolutionary capabilities to solve this natively:

  • BigQuery Property Graph: Allows you to define graph models (nodes and edges) directly over existing BigQuery tables without moving, transforming, or duplicating data (Zero-Copy Architecture). You can query graph paths using ISO/IEC GQL syntax and GoogleSQL's GRAPH_TABLE operator.
  • Semantic Measures (MEASURE(...)): Embeds business aggregation formulas directly into graph nodes. Combined with the GRAPH_EXPAND table-valued function, BigQuery automatically evaluates metrics at their correct entity grain, completely eliminating Cartesian join explosion!
Pre-Approved Public Dataset: In this codelab, we use Google's official, pre-approved public dataset bigquery-public-data.thelook_ecommerce. This eliminates any data approval roadblocks, requires zero custom CSV downloads or storage bucket creation, and works out of the box in your Google Cloud project.

3. Creating Schema & Tables

In this step, you will set up your graph workspace dataset thelook_graph, create reference views for marketing campaigns and enriched touchpoints, and create the pre-calculated attribution edge table.

Architecture Diagram

[campaigns] <──(generated_by)── [touchpoints] <──(engaged_with)── [users] │ (influenced) ▼ [products] <──(is_product)── [order_items] ──(belongs_to)──> [orders]
Zero-Copy Advantage: Base e-commerce tables (users, orders, order_items, products) reside directly in Google's pre-approved bigquery-public-data.thelook_ecommerce. You only create the reference views marketing_campaigns and touchpoints, and the attribution edge table edge_influenced in your local dataset!
SQL 
-- 1. Create Graph Workspace Dataset
CREATE SCHEMA IF NOT EXISTS `thelook_graph`
OPTIONS (
  location = 'US',
  description = 'Marketing Attribution & ROAS Graph using thelook_ecommerce'
);

-- 2. Create Marketing Campaigns Reference View
-- Defines top-of-funnel upstream campaigns across 5 channels with budgets and target ROAS
CREATE OR REPLACE VIEW `thelook_graph.marketing_campaigns` AS
SELECT 'Paid Search' AS channel, 'Q4_Search_Generic_Audio' AS campaign_name, 1500000.0 AS total_budget, 4.0 AS target_roas UNION ALL
SELECT 'Paid Search', 'Q4_Search_Brand_Electronics', 1100000.0, 5.0 UNION ALL
SELECT 'Paid Social', 'Q4_Meta_IG_Retargeting', 250000.0, 4.5 UNION ALL
SELECT 'Video', 'Q4_YouTube_Video_Awareness', 220000.0, 2.5 UNION ALL
SELECT 'Paid Social', 'Q4_TikTok_Prospecting_GenZ', 150000.0, 3.0 UNION ALL
SELECT 'Email Marketing', 'Q4_Email_Cart_Abandonment', 75000.0, 10.0 UNION ALL
SELECT 'Email Marketing', 'Q4_Email_VIP_Weekly_Drop', 60000.0, 8.0 UNION ALL
SELECT 'Organic', 'Organic_Search_SEO', 25000.0, 15.0;

-- 3. Create Enriched Touchpoints View (over public web events)
-- Maps public web events to realistic Q4 ad campaigns and assigns benchmark CPCs
CREATE OR REPLACE VIEW `thelook_graph.touchpoints` AS
SELECT
  e.id AS touchpoint_id,
  e.user_id,
  e.session_id,
  e.created_at,
  e.event_type,
  e.browser,
  e.traffic_source,
  CASE
    WHEN e.traffic_source = 'Adwords' AND MOD(e.id, 2) = 0 THEN 'Q4_Search_Generic_Audio'
    WHEN e.traffic_source = 'Adwords' THEN 'Q4_Search_Brand_Electronics'
    WHEN e.traffic_source = 'Facebook' AND MOD(e.id, 2) = 0 THEN 'Q4_Meta_IG_Retargeting'
    WHEN e.traffic_source = 'Facebook' THEN 'Q4_TikTok_Prospecting_GenZ'
    WHEN e.traffic_source = 'YouTube' THEN 'Q4_YouTube_Video_Awareness'
    WHEN e.traffic_source = 'Email' AND MOD(e.id, 2) = 0 THEN 'Q4_Email_Cart_Abandonment'
    WHEN e.traffic_source = 'Email' THEN 'Q4_Email_VIP_Weekly_Drop'
    ELSE 'Organic_Search_SEO'
  END AS campaign_name,
  CASE
    WHEN e.traffic_source = 'Adwords' THEN 'Paid Search'
    WHEN e.traffic_source = 'Facebook' THEN 'Paid Social'
    WHEN e.traffic_source = 'YouTube' THEN 'Video'
    WHEN e.traffic_source = 'Email' THEN 'Email Marketing'
    ELSE 'Organic'
  END AS channel,
  CASE
    WHEN e.traffic_source = 'Adwords' AND MOD(e.id, 2) = 0 THEN 3.78
    WHEN e.traffic_source = 'Adwords' THEN 2.64
    WHEN e.traffic_source = 'Facebook' AND MOD(e.id, 2) = 0 THEN 1.85
    WHEN e.traffic_source = 'Facebook' THEN 0.99
    WHEN e.traffic_source = 'YouTube' THEN 0.85
    WHEN e.traffic_source = 'Email' AND MOD(e.id, 2) = 0 THEN 0.12
    WHEN e.traffic_source = 'Email' THEN 0.10
    ELSE 0.00
  END AS cpc_cost
FROM `bigquery-public-data.thelook_ecommerce.events` e;

-- 4. Create Attributed Edge Table: edge_influenced
-- Pre-calculates First-Touch, Last-Touch, and Linear attribution weights over a 30-day window
CREATE OR REPLACE TABLE `thelook_graph.edge_influenced` AS
WITH ranked_touchpoints AS (
  SELECT
    t.touchpoint_id,
    o.order_id,
    t.campaign_name,
    t.channel,
    t.cpc_cost,
    t.created_at AS event_timestamp,
    o.created_at AS order_timestamp,
    ROW_NUMBER() OVER (PARTITION BY o.order_id ORDER BY t.created_at ASC) AS touchpoint_asc,
    ROW_NUMBER() OVER (PARTITION BY o.order_id ORDER BY t.created_at DESC) AS touchpoint_desc,
    COUNT(*) OVER (PARTITION BY o.order_id) AS total_touchpoints
  FROM `bigquery-public-data.thelook_ecommerce.orders` o
  JOIN `thelook_graph.touchpoints` t
    ON o.user_id = t.user_id 
   AND t.created_at <= o.created_at
   AND t.created_at >= TIMESTAMP_SUB(o.created_at, INTERVAL 30 DAY)
  WHERE o.status NOT IN ('Cancelled', 'Returned')
)
SELECT
  touchpoint_id,
  order_id,
  campaign_name,
  channel,
  cpc_cost,
  touchpoint_asc AS touchpoint_rank,
  total_touchpoints,
  ROUND(TIMESTAMP_DIFF(order_timestamp, event_timestamp, HOUR) / 24.0, 1) AS days_to_convert,
  IF(touchpoint_asc = 1, 1.0, 0.0) AS first_touch_weight,
  IF(touchpoint_desc = 1, 1.0, 0.0) AS last_touch_weight,
  ROUND(1.0 / total_touchpoints, 6) AS linear_weight
FROM ranked_touchpoints;

4. Declaring Property Graph & Measures

flag 🎯 Milestone Checkpoint 1: Zero-Copy Property Graph Modeling
Objective in Action: Rather than maintaining separate graph databases or copying millions of rows, BigQuery Property Graph maps directly to public tables and local views. In this step, we create the single, unified enterprise property graph thelook_graph.eCommerce_Integrated with 10 semantic measures.

Create Unified Property Graph DDL

SQL 
CREATE OR REPLACE PROPERTY GRAPH `thelook_graph.eCommerce_Integrated`
NODE TABLES (
  -- 1. Marketing Campaigns Node Table
  `thelook_graph.marketing_campaigns` AS campaigns
    KEY (campaign_name)
    LABEL campaigns PROPERTIES (
      campaign_name,
      channel,
      total_budget,
      target_roas,
      MEASURE(SUM(total_budget)) AS total_campaign_budget
    ),

  -- 2. Marketing Touchpoints Node Table
  `thelook_graph.touchpoints` AS touchpoints
    KEY (touchpoint_id)
    LABEL touchpoints PROPERTIES (
      touchpoint_id,
      user_id,
      session_id,
      campaign_name,
      channel,
      cpc_cost,
      event_type,
      browser,
      created_at,
      MEASURE(SUM(cpc_cost)) AS total_ad_spend,
      MEASURE(COUNT(touchpoint_id)) AS total_clicks,
      MEASURE(COUNT(DISTINCT user_id)) AS unique_reach
    ),

  -- 3. Users Node Table
  `bigquery-public-data.thelook_ecommerce.users` AS users
    KEY (id)
    LABEL users PROPERTIES (
      id,
      first_name,
      last_name,
      email,
      age,
      gender,
      country,
      traffic_source,
      created_at,
      MEASURE(COUNT(DISTINCT id)) AS total_users
    ),

  -- 4. Orders Node Table
  `bigquery-public-data.thelook_ecommerce.orders` AS orders
    KEY (order_id)
    LABEL orders PROPERTIES (
      order_id,
      user_id,
      status,
      created_at,
      num_of_item,
      MEASURE(COUNT(order_id)) AS total_orders
    ),

  -- 5. Order Items Node Table (Line-Item Financial Leaf Grain)
  `bigquery-public-data.thelook_ecommerce.order_items` AS order_items
    KEY (id)
    LABEL order_items PROPERTIES (
      id,
      order_id,
      user_id,
      product_id,
      sale_price,
      status,
      created_at,
      MEASURE(SUM(sale_price)) AS gross_revenue,
      MEASURE(COUNT(id)) AS total_items_sold
    ),

  -- 6. Products Catalog Node Table
  `bigquery-public-data.thelook_ecommerce.products` AS products
    KEY (id)
    LABEL products PROPERTIES (
      id,
      cost,
      category,
      name,
      brand,
      retail_price,
      department,
      MEASURE(AVG(cost)) AS avg_cost,
      MEASURE(AVG(retail_price)) AS avg_retail_price
    )
)
EDGE TABLES (
  -- Touchpoint -> Campaign (GENERATED_BY)
  `thelook_graph.touchpoints` AS touchpoint_campaign
    KEY (touchpoint_id)
    SOURCE KEY (touchpoint_id) REFERENCES touchpoints (touchpoint_id)
    DESTINATION KEY (campaign_name) REFERENCES campaigns (campaign_name)
    LABEL GENERATED_BY NO PROPERTIES,

  -- User -> Touchpoint (ENGAGED_WITH)
  `thelook_graph.touchpoints` AS user_touchpoint
    KEY (touchpoint_id)
    SOURCE KEY (user_id) REFERENCES users (id)
    DESTINATION KEY (touchpoint_id) REFERENCES touchpoints (touchpoint_id)
    LABEL ENGAGED_WITH NO PROPERTIES,

  -- Touchpoint -> Order (INFLUENCED)
  `thelook_graph.edge_influenced` AS edge_influenced
    KEY (touchpoint_id, order_id)
    SOURCE KEY (touchpoint_id) REFERENCES touchpoints (touchpoint_id)
    DESTINATION KEY (order_id) REFERENCES orders (order_id)
    LABEL INFLUENCED PROPERTIES (
      campaign_name,
      channel,
      cpc_cost,
      touchpoint_rank,
      total_touchpoints,
      days_to_convert,
      first_touch_weight,
      last_touch_weight,
      linear_weight
    ),

  -- Order Item -> Order (BELONGS_TO)
  `bigquery-public-data.thelook_ecommerce.order_items` AS item_order
    KEY (id)
    SOURCE KEY (id) REFERENCES order_items (id)
    DESTINATION KEY (order_id) REFERENCES orders (order_id)
    LABEL BELONGS_TO NO PROPERTIES,

  -- Order Item -> Product (IS_PRODUCT)
  `bigquery-public-data.thelook_ecommerce.order_items` AS item_product
    KEY (id)
    SOURCE KEY (id) REFERENCES order_items (id)
    DESTINATION KEY (product_id) REFERENCES products (id)
    LABEL IS_PRODUCT NO PROPERTIES
);
Schema Cleanliness: Structural edges (GENERATED_BY, ENGAGED_WITH, BELONGS_TO, IS_PRODUCT) use NO PROPERTIES. Attribution weights and touchpoint rankings are defined only on INFLUENCED.

5. Introspecting Semantic Measures

flag 🎯 Milestone Checkpoint 2: Semantic Measures Metadata Verification
Objective in Action: Verify that BigQuery registers the unified property graph and synthesizes declared MEASURE(...) expressions into first-class typed properties on node entities.

Inspect Declared Measures via INFORMATION_SCHEMA

Because measures are registered within the Property Graph schema rather than on physical tables, they are cataloged under INFORMATION_SCHEMA.PROPERTY_GRAPHS. We can query its metadata to inspect all declared measures, their aggregation formulas, and their synthesized measure types:

SQL 
SELECT
  JSON_VALUE(node_table_json, "$.name") AS node_table_name,
  JSON_VALUE(prop_json, "$.name") AS measure_name,
  JSON_VALUE(prop_json, "$.expression") AS measure_expression,
  CONCAT("MEASURE<", JSON_VALUE(prop_json, "$.dataType.typeKind"), ">") AS measure_type
FROM `thelook_graph.INFORMATION_SCHEMA.PROPERTY_GRAPHS`,
UNNEST(JSON_EXTRACT_ARRAY(property_graph_metadata_json, "$.nodeTables")) AS node_table_json,
UNNEST(JSON_EXTRACT_ARRAY(node_table_json, "$.labelAndProperties[0].properties")) AS prop_json
WHERE JSON_VALUE(prop_json, "$.expressionKind") = "MEASURE"
ORDER BY node_table_name, measure_name;

6. Cartesian Fan-Out Benchmark

error The Relational Anti-Pattern: Cartesian Multiplication
Objective in Action: Understand why traditional relational SQL fails when combining coarse upstream entities (campaign budgets) with fine leaf interactions (order items).

Standard Relational SQL Join Query

SQL 
SELECT
  c.channel,
  c.campaign_name,
  c.total_budget AS actual_campaign_budget,
  COUNT(*) AS joined_rows,
  ROUND(SUM(c.total_budget), 2) AS blown_up_budget,
  ROUND(SUM(c.total_budget) / c.total_budget, 0) AS budget_multiplication_factor,
  ROUND(SUM(oi.sale_price), 2) AS total_gross_sales
FROM `thelook_graph.marketing_campaigns` c
JOIN `thelook_graph.touchpoints` t
  ON c.campaign_name = t.campaign_name
JOIN `bigquery-public-data.thelook_ecommerce.orders` o
  ON t.user_id = o.user_id
JOIN `bigquery-public-data.thelook_ecommerce.order_items` oi
  ON o.order_id = oi.order_id
GROUP BY c.channel, c.campaign_name, c.total_budget
ORDER BY joined_rows DESC;

Why did this happen? Upstream vs. Downstream Variables:
  • Upstream Variables: Defined at a coarse grain (e.g. total_budget at the campaign level; 1 row per campaign).

  • When joining tables across cardinalities, upstream rows repeat on every single path. Applying a naive SUM() produces a disastrous 1,111,635x multiplication error!

7. Use Case 1: Top-of-Funnel Campaign Performance (GRAPH_EXPAND)

Marketing executives require a rich 8-column scorecard tracking macro budgets alongside micro interaction metrics (clicks, reach, spend, remaining budget, and effective CPC). They need this without writing complex subqueries or risking Cartesian duplication.

flag 🎯 Milestone Checkpoint: Multi-Grain Top-of-Funnel Performance at Root Grain
Objective in Action: Using BigQuery's GRAPH_EXPAND operator with declared MEASUREs and AGG(), we project macro budgets and interaction volumes without Cartesian duplication.

Standard SQL Query with GRAPH_EXPAND

SQL 
SELECT
  campaigns_channel AS channel,
  campaigns_campaign_name AS campaign_name,
  AGG(campaigns_total_campaign_budget) AS total_budget,
  AGG(touchpoints_total_clicks) AS total_clicks,
  AGG(touchpoints_unique_reach) AS unique_reach,
  ROUND(AGG(touchpoints_total_ad_spend), 2) AS total_ad_spend,
  ROUND(AGG(campaigns_total_campaign_budget) - AGG(touchpoints_total_ad_spend), 2) AS remaining_budget,
  ROUND(AGG(touchpoints_total_ad_spend) / NULLIF(AGG(touchpoints_total_clicks), 0), 2) AS effective_avg_cpc
FROM GRAPH_EXPAND("thelook_graph.eCommerce_Integrated", start_node => "touchpoints")
GROUP BY channel, campaign_name
ORDER BY total_ad_spend DESC;
Multi-Root Resolution: Specifying start_node => "touchpoints" anchors expansion to touchpoints, cleanly aggregating campaign budgets upstream via GENERATED_BY while rolling up interaction counts downstream.

8. Use Case 2: Multi-Touch Attribution (GRAPH_TABLE)

Compare the revenue assigned to each marketing campaign across three classic attribution models:

  1. First-Touch Attribution: Gives 100% of conversion credit to the customer's initial discovery campaign.
  2. Last-Touch Attribution: Gives 100% of conversion credit to the touchpoint immediately preceding the purchase.
  3. Linear Attribution: Distributes credit equally across all touchpoints in the customer's 30-day journey (∑ wi = 1.0).

Query with GRAPH_TABLE

SQL 
SELECT
  campaign_name,
  channel,
  ROUND(SUM(sale_price * first_touch_weight), 2) AS first_touch_revenue,
  ROUND(SUM(sale_price * last_touch_weight), 2) AS last_touch_revenue,
  ROUND(SUM(sale_price * linear_weight), 2) AS linear_revenue
FROM GRAPH_TABLE(`thelook_graph.eCommerce_Integrated`
  MATCH (t:touchpoints)-[i:INFLUENCED]->(o:orders)<-[:BELONGS_TO]-(oi:order_items)
  COLUMNS (
    t.campaign_name AS campaign_name,
    t.channel AS channel,
    oi.sale_price,
    i.first_touch_weight,
    i.last_touch_weight,
    i.linear_weight
  )
)
GROUP BY campaign_name, channel
ORDER BY linear_revenue DESC;

9. Use Case 3: 4-Hop Profitability & Margin % (GRAPH_TABLE)

Evaluating campaigns solely on revenue is misleading. A campaign might generate high gross sales by promoting low-margin items. In this 4-hop traversal, we connect touchpoints to orders, line items, and product catalog costs to evaluate true Gross Profit and Gross Margin %.

flag 🎯 Milestone Checkpoint 3: Multi-Hop Profit Attribution at the Leaf Grain
Objective in Action: Using BigQuery's GRAPH_TABLE operator, we traverse 4 hops from touchpoints to products and apply leaf-grain weighted aggregations.
SQL 
SELECT
  campaign_name,
  channel,
  ROUND(SUM(sale_price * linear_weight), 2) AS attributed_revenue,
  ROUND(SUM(cost * linear_weight), 2) AS attributed_cogs,
  ROUND(SUM((sale_price - cost) * linear_weight), 2) AS gross_profit,
  ROUND(SAFE_DIVIDE(SUM((sale_price - cost) * linear_weight), SUM(sale_price * linear_weight)) * 100, 2) AS gross_margin_pct
FROM GRAPH_TABLE(`thelook_graph.eCommerce_Integrated`
  MATCH (t:touchpoints)-[i:INFLUENCED]->(o:orders)<-[:BELONGS_TO]-(oi:order_items)-[:IS_PRODUCT]->(p:products)
  COLUMNS (
    t.campaign_name AS campaign_name,
    t.channel AS channel,
    oi.sale_price,
    p.cost,
    i.linear_weight
  )
)
GROUP BY campaign_name, channel
ORDER BY gross_profit DESC;

11. Use Case 5: Unified Executive Scorecard

The Chief Marketing Officer needs a unified scorecard that combines:

  1. Top-of-Funnel Marketing Measures: Macro budget, actual ad spend, and remaining budget via GRAPH_EXPAND.
  2. Bottom-of-Funnel Profit Attribution: Attributed revenue, COGS, and gross profit via GRAPH_TABLE.
  3. Executive ROI: True ROAS on Spend vs. ROAS on Budget, and Gross Margin %.

Unified Single-Graph Dual Query

SQL 
WITH marketing_funnel AS (
  SELECT
    campaigns_channel AS channel,
    campaigns_campaign_name AS campaign_name,
    AGG(campaigns_total_campaign_budget) AS total_budget,
    AGG(touchpoints_total_clicks) AS total_clicks,
    AGG(touchpoints_unique_reach) AS unique_reach,
    ROUND(AGG(touchpoints_total_ad_spend), 2) AS total_ad_spend,
    ROUND(AGG(campaigns_total_campaign_budget) - AGG(touchpoints_total_ad_spend), 2) AS remaining_budget,
    ROUND(AGG(touchpoints_total_ad_spend) / NULLIF(AGG(touchpoints_total_clicks), 0), 2) AS effective_avg_cpc
  FROM GRAPH_EXPAND("thelook_graph.eCommerce_Integrated", start_node => "touchpoints")
  GROUP BY channel, campaign_name
),

sales_attribution AS (
  SELECT
    campaign_name,
    ROUND(SUM(sale_price * linear_weight), 2) AS attributed_revenue,
    ROUND(SUM(cost * linear_weight), 2) AS attributed_cogs,
    ROUND(SUM((sale_price - cost) * linear_weight), 2) AS gross_profit
  FROM GRAPH_TABLE(`thelook_graph.eCommerce_Integrated`
    MATCH (t:touchpoints)-[i:INFLUENCED]->(o:orders)<-[:BELONGS_TO]-(oi:order_items)-[:IS_PRODUCT]->(p:products)
    COLUMNS (
      t.campaign_name AS campaign_name,
      oi.sale_price,
      p.cost,
      i.linear_weight
    )
  )
  GROUP BY campaign_name
)

SELECT
  m.channel,
  m.campaign_name,
  m.total_budget,
  m.total_ad_spend,
  m.remaining_budget,
  m.effective_avg_cpc,
  s.attributed_revenue,
  s.gross_profit,
  ROUND(s.attributed_revenue / NULLIF(m.total_ad_spend, 0), 2) AS roas_on_spend,
  ROUND(s.attributed_revenue / NULLIF(m.total_budget, 0), 2) AS roas_on_budget,
  ROUND(SAFE_DIVIDE(s.gross_profit, s.attributed_revenue) * 100, 2) AS gross_margin_pct
FROM marketing_funnel m
JOIN sales_attribution s ON m.campaign_name = s.campaign_name
ORDER BY s.gross_profit DESC;

13. Decision Guide & Clean Up

When should you use each query operator in BigQuery? Use this architectural decision matrix:

Approach When to Use Why?
Plain SQL SUM() on Single Table Aggregating a column at its native table grain (e.g. SELECT SUM(total_budget) FROM marketing_campaigns). 100% safe. No joins exist to multiply rows.
Plain SQL SUM() across Multi-Table JOINs ❌ ANTI-PATTERN on 1:N or N:M relationships. Causes catastrophic Cartesian duplication (e.g. $60k becomes $66.7 Billion).
GRAPH_TABLE Network traversals, multi-hop paths, edge filtering, and leaf-grain weighted aggregations. Evaluates row-level expressions across paths. Safe for revenue/COGS because weights sum to 1.0 (∑ wi = 1.0).
GRAPH_EXPAND + AGG() Multi-grain BI rollups combining upstream measures (e.g. campaign budget) with downstream measures (e.g. total clicks, ad spend). Evaluates declared MEASUREs at their native entity grain independently, completely preventing fan-out errors.
